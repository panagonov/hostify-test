# Hostify QA — автоматизирани тестове срещу продукцията

Това хранилище е тестовият комплект на Hostify: номерирани Playwright сценарии, които отварят истински
браузър срещу **https://hostify.bioseek.eu/app/**, минават през всяка страница на менюто, въвеждат данни
през формите и проверяват екраните така, както ги проверява QA човек — непреведени текстове, отрязани
елементи, слаб контраст, счупен лейаут, грешки и предупреждения в конзолата, неуспешни заявки.

Подробните правила (на английски, за агента): `CLAUDE.md` и `docs/`.

## Първо пускане

```bash
git clone https://github.com/panagonov/hostify-test.git && cd hostify-test
npm run qa:setup                 # зависимости + Chromium (веднъж)
cp .env.example .env             # попълни QA_SUPERADMIN_EMAIL / QA_SUPERADMIN_PASSWORD и QA_ADMIN_PASSWORD
npm run qa:run -- --only 001     # първият тест: вход в суперадмин конзолата
```

`.env` никога не се качва в git. Паролата на администратора на QA акаунта (`QA_ADMIN_PASSWORD`) е
„известната парола“ — с нея и `qa.admin@hostify-qa.test` можеш да влезеш в акаунта „QA Automation“ и сама
да гледаш какво са направили тестовете.

## Кой пуска тестовете

Ти казваш на агента (Claude Code в това хранилище) какво да пусне — един тест, блок или всичко; агентът ги
пуска. Тестовете вървят един по един и преди всеки агентът изписва „пускам тест 005-platform-pages — проверка
на навбар менютата…“, а след всеки — „завърши без грешка“ или „N казуса за решаване“ с имената им. Казусите от
един пуск се записват в една папка `reports/issues/<версия>/<дата час>/` (напр. `1.0.3/2026-11-05 13:00`, най-новите най-долу):
по един md файл на тест с какво се е объркало, как се възпроизвежда и скрийншотите, плюс `README.md` със
списъка. Тази папка се подава на агента в проекта Hostify, който анализира и поправя. `npm run qa:publish` я
качва в хранилището.

## Версията на приложението

Всеки пуск знае срещу коя версия е минал: тя е във футера на навбара (`v 1.0.3`; клик отваря историята на
промените) и идва с всеки отговор на API. Казусите стоят под папката на версията. Ако версията е същата като
при предишния пуск, повтарящ се казус е отбелязан „известен от …“ — нов е само това, което не е било. При нова
версия агентът първо чете `reports/issues/<версия>/release-notes.md` (новостите и поправките) и казва на кои
тестове да се обърне внимание.

## Всекидневна работа

| Какво | Команда |
|---|---|
| цялата верига по ред (или кажи на агента) | `npm run qa:run` |
| един спек / блок | `npm run qa:run -- --only 002` · `npm run qa:run -- --from 100 --to 199` |
| без прозорец на браузъра (фон, CI) | `npm run qa:run:headless` (или `-- --headless`); по подразбиране браузърът е видим |
| спиране | `npm run qa:stop` |
| докъде е стигнало | `npm run qa:status` |
| резултатът на последния пуск | `npm run qa:summary` (текст) · `npm run qa:report` (HTML с трейсове) |
| споделяне с разработчиците | `npm run qa:publish` — копира резултата в `reports/published/<пуск>/`, комитва и пушва |
| бележка за нещо, което тестовете пропускат | `npm run qa:feedback "кратко заглавие"` → `feedback/<дата>-<slug>.md` + скрийншот до него |

Резултатът на всеки пуск е в `reports/runs/<дата_час>/summary.md`: първо провалените тестове (грешка,
скрийншот), после какво е казала конзолата на браузъра във всеки тест, после визуалните находки по екран
(контраст, отрязан текст — тях ги преценява окото), накрая таблица с всички тестове. До него е скрийншот на
всеки проверен екран.

## Редът на тестовете

Тестовете са номерирани и се изпълняват строго по ред с един браузър: 001 влиза като суперадминистратор,
002 създава акаунта „QA Automation“ и неговия администратор (и преди това чисти всичко, което предишният
пуск е създал), 003 влиза като администратора, 005 и 010 отварят всяка страница от менюто, 1xx–9xx пълнят
страниците по реда на зависимостите им (първо настройките, после обектите, после цените, резервациите…).
По-късен тест разчита на данните на по-ранен — затова един пуск на цялата верига е „истината“, а пуск на
един спек е за отстраняване на проблем.

## Обучаване на тестовете

Когато видиш нещо, което според теб не е наред, а тестовете са зелени: `npm run qa:feedback "…"`, попълни
бележката, сложи скрийншота до нея и в Claude Code напиши `/qa-teach feedback/<файл>.md`. Агентът
възпроизвежда проблема на продукцията, пише тест, който е ЧЕРВЕН заради него, и отбелязва бележката. С
`npm run qa:publish` бележката и червеният тест стигат до разработчиците; когато поправят, тестът става зелен.

Умения в Claude Code: `/qa-run` (пускане и четене на резултат), `/qa-page` (тест за страница),
`/qa-teach` (обучение), `/qa-selectors` (селектори).

## QA акаунтът е нормален акаунт

„QA Automation“ е обикновен клиентски акаунт, отбелязан като `qaAccount`: платформата никога не го спира
(изтекъл Trial, неплатени сметки) и не го таксува, затова плановете и функциите му се сменят безнаказано — и
това е единствената разлика. Нищо не му се налага предварително: страница, която иска план или функция, се
тества от спек, който я включва през формите, проверява ефекта и може да я върне. Спек 100 създава по един
потребител за всяка роля (мениджър, property manager, revenue manager, booking agent, счетоводител, team
supervisor, housekeeper) с известната парола `QA_USERS_PASSWORD` (или тази на администратора), така че тестовете
влизат от името на всяка роля.

## Какво НЕ правят тестовете

Не пипат чужди акаунти — работят само в „QA Automation“. Не трият акаунта и администратора му. Не пращат
истински имейли и SMS (адресите са `.test`). Не въвеждат данни през API — само през формите, както човек.
